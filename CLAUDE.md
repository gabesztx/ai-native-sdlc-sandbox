# Feature Request Board — AI-native SDLC sandbox

A learning sandbox that follows Anthropic's AI-Native SDLC Playbook. The product is a
small Feature Request Board (submit requests, vote, track status); the real subject is
the agent workflow around it: intent → spec → plan → build → review.

## Status

The app is NOT scaffolded yet. Only the agent configuration exists. Commands below are
the target interface — if a command does not exist yet, say so instead of inventing one.

## Stack

- **Web** (`apps/web`): Angular 22 — standalone components, signals, zoneless,
  built-in control flow (`@if`, `@for`). Tests: Vitest.
- **API** (`apps/api`): Java 25 + Spring Boot 4.1, Maven wrapper (`./mvnw`).
- **Database**: SQLite (single file) + Flyway migrations. Data access via Spring
  `JdbcClient` with plain SQL — no JPA.
- **Contract**: OpenAPI generated by springdoc, exported to `contracts/openapi.json`
  (committed). The Angular client is generated from it, never hand-written.

## Repo map

```
CLAUDE.md                 shared rules (this file)
REVIEW.md                 review severity rules
apps/web/                 Angular app        (has its own CLAUDE.md)
apps/api/                 Spring Boot API    (has its own CLAUDE.md)
contracts/openapi.json    API contract (generated, committed)
docs/changes/<id>-<slug>/ intent.md, spec.md, plan.md per change
.claude/skills/           SDLC procedures: intent, spec, plan, review
.claude/agents/           specialist subagents (verifier, reviewers)
```

## Commands (target)

- `pnpm check` — the single verification command: web lint + test + build, then
  `./mvnw verify`. This is the feedback loop.
- `pnpm dev` — run web and API locally.
- Single test: `pnpm --filter web test -- <pattern>` / `./mvnw -pl apps/api test -Dtest=<Class>`.

## Definition of done

Never report a task as done until `pnpm check` passes. Paste the summary line of the
result. If it fails, report the failure — do not hide it, skip it, or weaken a test.

## SDLC workflow

Every non-trivial change follows this chain. Each step writes a file and stops for
human approval before the next step.

1. `/intent` → `docs/changes/<id>-<slug>/intent.md` — problem, outcome, open questions
2. `/spec`   → `spec.md` — behaviour, API, data model, acceptance criteria
3. `/plan`   → `plan.md` — ordered steps, files touched, tests. **Human approval gate.**
4. Build — implement `plan.md` only; run `pnpm check`; verifier subagent confirms
5. `/review` → parallel reviewer subagents, merged per `REVIEW.md`

Trivial changes (typo, config tweak) may skip to step 4, but say that you are skipping.

## Working with agents

- The main session is the **orchestrator**. It delegates to subagents in
  `.claude/agents/` and only receives their summaries.
- Agents hand work to each other through files in `docs/changes/`, not through chat.
  If it is not in `intent.md` / `spec.md` / `plan.md`, it was not agreed.
- The agent that wrote the code never reviews it. Review is done by reviewer subagents.
- Reviewers and the verifier are read-only: they report, they do not edit.
- Parallel work: one task = one git worktree = one branch = one PR.

## Architecture rules

- API changes start in `spec.md`, then code, then the regenerated `contracts/openapi.json`.
- Schema changes only via a new Flyway migration (`V<n>__<description>.sql`).
- Package the API by feature (`request/`, `vote/`), not by layer.

## Conventions

- Code, comments, docs and commit messages in English.

## Boundaries

- Ask before adding a dependency.
- Never edit a test to make it pass; fix the code, or report why the test is wrong.
- Never edit an existing Flyway migration; add a new one.
- Never commit secrets or `.env` files; never read `.env` files.
- Never force-push.
